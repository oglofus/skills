# Accessibility statement

Oglofus wants its projects, documentation, command-line tools, and contribution workflows to be usable by people with different abilities, assistive technologies, devices, and environments.

## Our goals

We aim to:

- Use clear structure, plain language, descriptive links, and meaningful text alternatives.
- Prefer native, semantic controls and predictable keyboard interaction in interfaces.
- Preserve visible focus, readable contrast, and meaning that does not depend on color alone.
- Respect reduced-motion preferences and avoid unnecessary flashing or auto-advancing content.
- Make issue and pull-request workflows predictable and usable with assistive technology.

This is an ongoing commitment, not a claim that every project is fully accessible today. Known limitations should be documented with a workaround when one exists.

## Reporting an accessibility barrier

Use the [accessibility issue form](https://github.com/oglofus/skills/issues/new?template=accessibility.yml). Include the task you were trying to complete, expected and actual behavior, reproduction steps, environment, and any assistive technology or accessibility settings involved. If the report contains security-sensitive information, follow [the security policy](SECURITY.md) instead.

## Contribution and testing guidance

For applicable changes, contributors should check keyboard-only operation, visible focus, labels and announced errors, color-independent meaning, reduced motion, screen-reader behavior, zoom/reflow, and high-contrast or forced-colors modes. Documentation should use logical headings, descriptive links, real lists, and text alternatives for meaningful visuals.

See the [Accessibility Best Practices for Your Project](https://opensource.guide/accessibility-best-practices-for-your-project/) guide for practical guidance and the [contributing guide](CONTRIBUTING.md) for this repository's workflow.
